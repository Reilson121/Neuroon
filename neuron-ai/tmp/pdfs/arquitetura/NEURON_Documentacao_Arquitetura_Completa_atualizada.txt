Documentação Completa da Arquitetura do MVP (versão atualizada)
React + Spring Boot + PostgreSQL/pgvector + FastAPI + LangChain/LangGraph
Status: arquitetura-base aprovada. Este documento consolida as decisões técnicas tomadas até esta
etapa e identifica explicitamente o que ainda está em aberto.
O que mudou nesta versão: (1) o monitor humano está fora do escopo atual; (2) entra a
arquitetura da prática com questões, apenas em disciplinas com prova (seção 7); (3) entra o
feedback da plataforma (seção 12). Itens marcados como (proposta) ainda precisam ser
validados pela equipe; os pontos em aberto estão na seção 30.
1. Objetivo arquitetural
A arquitetura do NEURON foi desenhada para separar a aplicação web, as regras de negócio e o
serviço especializado de IA. O Spring Boot é o backend principal e funciona como porta de
entrada para o front-end. O serviço Python é interno e dedicado ao Monitor Virtual e à prática
com questões.
Princípio central
React
 |
 v
Spring Boot
 |----> PostgreSQL + pgvector
 |
 +----> FastAPI
          |
          +--> LangChain / LangGraph
                  |
                  +--> LLM / Embeddings
O React não acessa diretamente o FastAPI nem recebe chaves de provedores de IA. Isso reduz
acoplamento, concentra autenticação e autorização no backend principal e permite substituir
componentes internos sem alterar a interface pública.

3. Visão de contexto
[Estudante] -------- > [ NEURON ] ----> [Provedor LLM/Embeddings]
                     /
[Administrador] ----/ |
                      +-------> [Armazenamento de arquivos]
O Estudante consulta conteúdos, utiliza o Monitor Virtual, pratica com questões (nas disciplinas
com prova) e envia feedback sobre a plataforma. O Administrador publica e organiza conteúdo,
gerencia a base de conhecimento e consulta o feedback. Serviços externos de IA e
armazenamento são dependências controladas pelo backend/serviço interno.
Fora do escopo atual: o monitor humano (monitoria entre estudantes, candidatura,
agendamentos, mensagens e avaliações de monitores) fica para uma fase futura e não tem
componentes nesta arquitetura.

6. Arquitetura do Monitor Virtual
O Monitor Virtual usa RAG. A disciplina é obrigatória para o chat; o assunto é opcional. A
recuperação deve respeitar esses filtros e utilizar apenas materiais autorizados como fonte do
Monitor Virtual.
Pergunta

   v
Classificar
   |
   v
Recuperar Top-K (filtros de disciplina/assunto)
   |
   v
Contexto suficiente?
   | SIM                  | NAO
   v                      v
Gerar resposta        Reescrever consulta
+ fontes                  |
   |                      +--> nova recuperação
   v                           máximo de 2 tentativas
Streaming                      |
                               v
                        Fallback sem inventar
Fallback previsto: quando não houver contexto suficiente, o sistema informa que não encontrou
informações suficientes nos materiais da disciplina, em vez de produzir uma resposta
apresentada como fundamentada.
7. Arquitetura da prática com questões (novo)
A prática permite que o aluno resolva questões no padrão de cobrança dos professores, a partir
das listas de exercícios e provas cadastradas. Ela reaproveita a base vetorial e o serviço de IA,
com regras próprias.

9. Streaming SSE
A API pública do Monitor Virtual retorna text/event-stream. Como a requisição é POST com JSON,
o front-end deverá consumir o fluxo com fetch/ReadableStream ou biblioteca compatível com
SSE via POST; EventSource nativo não deve ser assumido para esse endpoint.
event: token
data: {"texto":"A arquitetura"}
event: token
data: {"texto":" de Von Neumann..."}
event: sources
data: {"fontes":[...]}
event: done
data: {}

          |
          v
      embeddings
          |

Ao cadastrar ou alterar um Material marcado como fonte do Monitor Virtual, o backend solicita
indexação. Ao desativá-lo, os chunks derivados devem ser removidos. Ao substituir o documento,
os chunks antigos são removidos e o material é reindexado.
Listas de exercícios e provas (novo): seguem o mesmo fluxo. Para esses materiais, o
chunking deve preservar a estrutura de questões (uma questão por chunk, com número da
questão e gabarito quando houver); esse detalhe será validado na etapa de materiais. Materiais
disponíveis para prática também são indexados, mesmo que não sejam fonte do Monitor Virtual
(proposta).

12. Feedback da plataforma (novo)
O estudante autenticado envia uma avaliação e um comentário sobre a plataforma. O Spring
Boot valida e grava o registro na tabela feedback_plataforma; o administrador consulta os
retornos por endpoint administrativo. Esse fluxo não passa pelo serviço de IA. Ele substitui a tela
de avaliações de monitores do protótipo anterior, que pertencia ao monitor humano.
O formato exato (escala da nota, categorias, comentário livre e anonimato) está em aberto
(seção 30).

22. Segurança arquitetural
O Spring Boot centraliza autenticação e autorização. Estudantes possuem acesso de consulta,
Monitor Virtual, prática e envio de feedback; administradores possuem acesso aos endpoints de
administração, incluindo a consulta ao feedback. As chaves de LLM/embeddings permanecem no
ambiente do serviço Python e nunca são enviadas ao front-end.

Conclusão
A arquitetura aprovada mantém o NEURON modular sem introduzir infraestrutura excessiva para
o MVP. Spring Boot concentra o domínio e a segurança; React permanece desacoplado da IA; o
serviço Python especializa o RAG e a prática com questões; e PostgreSQL + pgvector simplifica
persistência e busca vetorial em uma única tecnologia de banco. A estrutura permite evolução
posterior, inclusive a futura volta do monitor humano, sem tornar o Monitor Virtual responsável
pelo restante do sistema.
